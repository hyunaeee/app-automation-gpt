# 프로젝트 진행 방식

Launchpad는 아이디어를 입력할 때 **한 번에 자동으로** 또는 **단계별로 확인**하는 방식을 선택할 수 있습니다. 두 방식 모두 기획 이후에는 같은 코드 생성, 실행 검증, 오류 수정, 결과물 전달 흐름을 사용합니다.

## 한 번에 자동으로

기본 진행 방식입니다. 아이디어를 입력하면 요구사항 분석부터 결과물 생성까지 이어서 실행합니다. 기존 프로젝트와 진행 방식을 지정하지 않은 요청도 이 방식을 사용합니다.

## 단계별로 확인

프로젝트를 만들기 전에 **단계별로 확인**을 선택합니다. 에이전트는 아래 세 지점에서 멈추고 사용자의 확인을 기다립니다.

| 확인 시점 | 검토할 내용 | 확인 후 이어지는 작업 |
| --- | --- | --- |
| 기획 | 만들려는 서비스의 목적, 사용자, 범위와 가정 | 기능 정의 |
| 기능 | 핵심 기능과 추가 기능 | 기술 스택과 구조 설계 |
| 설계 | 기술 스택과 파일 구조 | 프로젝트 생성, 코드 구현, 테스트, 오류 수정, 결과물 생성 |

각 화면에서 **확인하고 다음 단계**를 누르면 이어집니다. 설계까지 확인하기 전에는 구현 파일을 만들지 않습니다. 대기 중인 프로젝트는 목록에서 다시 열거나 페이지를 새로고침해도 현재 확인 지점을 유지합니다.

설계 확인 이후에는 구현과 테스트를 단계마다 다시 확인하지 않습니다. 자동 검증이 실패하면 정해진 재시도 횟수 안에서 수정을 시도하며, 해결되지 않은 문제는 실패 상태와 검사 로그로 표시합니다. 테스트를 통과하면 실행 가능한 미리보기와 소스 다운로드를 제공합니다.

## 계획을 바꾸고 싶을 때

AI 연결이 있는 프로젝트는 확인 화면에서 변경 요청을 전달해 계획을 다시 검토할 수 있습니다. 변경 요청은 기획 전체를 다시 검토하므로 기존 승인을 초기화하고 기획 확인부터 다시 시작합니다. 수정된 내용은 다시 확인해야 하며, 이전 확인 화면의 승인으로 새 계획을 건너뛸 수 없습니다.

AI 연결이 없는 로컬 템플릿 모드에서도 세 번의 확인 흐름을 체험할 수 있습니다. 이 모드에서는 자연어 피드백을 AI가 반영하는 기능을 제공하지 않습니다. 기본 템플릿이 지원하는 범위를 확인하고 진행하거나, AI를 연결한 뒤 새 프로젝트를 만듭니다.

실행 검증 통과는 모든 업무 요구사항이나 실제 서비스 운영 품질을 보장하지 않습니다. 완성된 앱을 사용해 보고 추가 변경을 요청할 수 있으며, 공개 배포나 외부 서비스 연결은 결과물의 별도 설정을 따릅니다.

## 승인 요청의 일관성

확인 요청에는 현재 검토의 고유 ID가 포함됩니다. 서버는 프로젝트 소유권과 현재 확인 상태를 함께 검증합니다. 이미 처리된 검토, 다른 단계의 ID 또는 오래된 화면에서 보낸 요청은 충돌로 거부합니다. 이 경우 프로젝트를 다시 불러와 최신 내용을 확인합니다.

확인 대기는 프로젝트 오류와 별개의 상태입니다. 대기 상태를 실패로 표시하거나 자동 재시도로 넘기지 않으며, 사용자의 확인 없이는 다음 단계가 실행되지 않습니다.

프로젝트 생성 요청은 `workflowMode: "auto" | "guided"`를 사용합니다. 진행 방식을 생략하면 `auto`입니다. 확인 대기 시 프로젝트의 `status`는 `awaiting_approval`이며 `review`에 `id`, `stage`, `createdAt`을 담습니다. `stage`는 `requirements`, `features`, `architecture` 중 하나입니다.

확인은 `POST /api/projects/:id/review`에 `{ "reviewId": "현재 검토 ID", "action": "approve" }`를 보냅니다. AI 계획 수정은 같은 경로에 `{ "reviewId": "현재 검토 ID", "action": "revise", "feedback": "변경 요청 내용" }`을 보냅니다. 피드백은 5~4,000자이며 AI 연결이 필요합니다. 오래된 검토 ID나 현재 상태에 맞지 않는 요청은 HTTP 409를 반환합니다.

`approvedStages`는 현재 계획에서 확인을 마친 단계를, `reviewHistory`는 확인·수정 요청의 단계, 동작, 시각과 수정 피드백을 기록합니다. 계획 수정으로 현재 승인이 초기화되어도 검토 이력은 남습니다.

## 검증 범위

`e2e/guided-workflow.spec.ts`는 API 키와 구독 크레딧을 사용하지 않는 로컬 템플릿 환경에서 다음 동작을 실제 브라우저로 확인합니다.

- 생성 화면에서 단계별 확인을 선택하고 첫 기획 확인에 도달하기
- 새로고침 이후 확인 상태와 검토 ID 유지하기
- 설계 승인 전 구현 파일이 비어 있는지 확인하기
- 기획 → 기능 → 설계 순서로만 진행하기
- 지난 검토 ID로 다시 승인하면 충돌 응답 받기
- 설계 확인 이후 자동 구현과 검증을 마치고 실행 결과 받기

AI 피드백이 요구사항을 얼마나 잘 반영하는지는 이 로컬 브라우저 테스트의 검증 범위에 포함하지 않습니다.

## Vercel 운영

승인 대기 상태와 명세는 비공개 Blob에 저장하며, 실행 슬롯을 반환한 뒤 Sandbox 중지를 요청합니다. `PUBLIC_APP_URL`을 외부에서 접근 가능한 HTTPS 서비스 주소로 설정하세요. 생략하면 `VERCEL_URL`을 사용합니다. 배포 보호를 사용하는 경우 `/api/internal/projects/:id/pause` 콜백이 서비스에 도달할 수 있도록 구성해야 합니다. 이 경로는 매 실행마다 바뀌는 비공개 토큰으로 인증하며 프로젝트 응답에 토큰을 포함하지 않습니다.

콜백이 실패하면 프로젝트 조회 시 중지를 재시도합니다. 상세 화면은 실행 중 약 1.3초, 승인 대기 중 약 10초 간격으로 조회합니다. 브라우저까지 닫힌 상태에서 콜백이 실패하면 Sandbox가 설정된 실행 제한 시간(TTL)까지 남아 비용이 발생할 수 있습니다. 실제 배포 후 콜백 도달 여부와 대기 중 Sandbox 중지를 확인해야 합니다. 승인 후에는 새 실행 ID로 작업을 이어가며, 이전 작업의 지연된 응답은 새 실행을 변경하거나 중지할 수 없습니다.
